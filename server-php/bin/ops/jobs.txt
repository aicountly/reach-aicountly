# Scheduled jobs of Reach (E8-OPS, F160). Installed into the deploy user's crontab by the production deploy
# (.github/workflows/deploy-production.yml -> bin/ops/post-deploy-jobs.sh -> bin/ops/install-jobs.sh --apply); check on
# the server with `bash bin/ops/install-jobs.sh --check`. `php spark reach:console-audit-deliver` reports itself to
# Console's Cron Job Monitor (reach.console_audit_deliver; app/Libraries/CronHeartbeat.php, key CONSOLE_CRON_MONITOR_KEY
# in api/.env, written by the deploy from the repo secret), so it runs WITHOUT the run-job.php wrapper — wrapping it
# with --monitor would report every run twice.
# The worker / blog / community crons (docs/operations/REACH_WORKER_AND_CRON.md) are not listed here yet: they stay
# hand-installed, and a hand-installed line for them is left alone.
#! app: reach
# CodeIgniter on its Postgre driver: the PHP CLI needs pgsql (not pdo_pgsql).
#! php-ext: pgsql
# Replaces the hand-installed line README.md used to give, so the job never runs twice. The spark command name is
# Reach's own.
#! legacy-pattern: spark[[:space:]]+reach:console-audit-deliver
# name                  | schedule    | command (run from the api folder)
console-audit-deliver   | */5 * * * * | {php} spark reach:console-audit-deliver
# Estate analytics (analytics-aicountly sdk/README.md). BOTH jobs are inert until
# AICOUNTLY_ANALYTICS_ENABLED=1 in .env: the flush exits 0 immediately and the snapshot prints one
# line and exits 0. That is why they are safe to install on every product, enabled or not — a job
# that mailed an error nightly until somebody configured it is a job the operator would filter, and
# then nobody would see the night it broke for a real reason.
# NOTE: this block asks install-jobs.sh for `pgsql` (CodeIgniter's Postgre driver). The analytics
# jobs use PDO and need pdo_pgsql as well; the server normally has both. If it does not, the job
# says so and exits 3 rather than failing obscurely — point it at a CLI that has both with
# `bash bin/ops/install-jobs.sh --php=/path/to/php --apply`.
# The flush drains anything the after-response send could not deliver (Analytics briefly down, a CLI
# process, a request that died before shutdown). The snapshot reports this product's own database
# size, tables and row counts once a day — events can never answer those, so the product that owns
# the database reports them (analytics docs/08). Minutes are staggered per product so forty hosts do
# not all wake together.
analytics-flush         | * * * * *   | {php} app/ThirdParty/AicountlyAnalytics/analytics-flush.php --env=.env
analytics-platform      | 51 1 * * *  | {php} app/ThirdParty/AicountlyAnalytics/analytics-platform-snapshot.php --env=.env --push
# This product also OWNS facts nothing else can report: marketing figures (campaigns, budgets, leads and the content pipeline).
analytics-snapshot      | 53 1 * * *  | {php} scripts/analytics_snapshot.php --env=.env --push
